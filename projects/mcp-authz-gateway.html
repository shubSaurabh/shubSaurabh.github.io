Case study · AI agent security

Putting a human and a policy between AI agents and their tools

mcp-authz-gateway applies the controls we already use for privileged humans (least privilege, just-in-time approval, short-lived grants and an audit trail) to AI agents that act through the Model Context Protocol.

The problem

AI agents such as Claude, Cursor and custom agents reach files, shells, databases and SaaS accounts through MCP servers. Most of those servers do whatever the agent asks. A single prompt injection hidden in a web page, an issue or a README can turn into rm -rf, a leaked .env file or a deleted repository. That is the same standing-privilege problem PAM solved for human administrators, and it needs the same answer.

How it works

The MCP client launches the gateway instead of the real server, and the gateway launches the real server. It relays JSON-RPC in both directions and only intervenes on tools/list (hiding tools that are always denied) and tools/call (enforcing policy). Everything else passes through untouched, so it works with any stdio MCP server.

rules:
  - name: never touch credentials
    tools: ["*"]
    effect: deny
    when:
      path: { glob: ["*/.ssh/*", "*/.aws/*", "*.pem", "*/.env"] }
  - name: shell needs a human
    tools: [run_command]
    effect: ask

Design decisions

  • Fail closed. Conditions on a missing argument, or on a value of the wrong type, never match. Unanswered approvals are denied after a timeout.
  • Normalize before matching. Paths are normalized first, so /projects/../../.ssh/id_rsa cannot pass a /projects/** rule.
  • No bypass through batching. JSON-RPC batches are split, and every call inside one is checked.
  • Approval where the human already is. If the client supports MCP elicitation, the prompt appears inside it. Otherwise the gateway sends a desktop notification and queues the request for a local console or the CLI.
  • Just-in-time, not forever. "Allow for 15 minutes" creates a grant that expires on its own and can be revoked, the same model as zero standing privilege for people.
  • Harden the approval console. It listens on localhost only and needs a random token in the URL, because any website can send requests to localhost. It also checks the Host header (against DNS rebinding) and sends a strict Content Security Policy.
  • Tamper-evident audit. Each record includes the hash of the one before it, so audit --verify detects edited or deleted records. Secrets are masked in arguments before they are logged.

What it does not do

It controls what an agent can ask a server to do. It does not sandbox the server, so servers still need minimal OS permissions. A tool that accepts free-form code can only be governed with approvals or regular expressions. The hash chain detects changes but cannot stop someone with write access from rewriting the whole log, so ship records to a SIEM when that matters. The README lists these limits so nobody relies on more than the gateway provides.

Testing

Unit tests cover the policy engine, rate limits, redaction and the audit chain, including tampering and deletion. End-to-end tests start the real gateway process and drive it over stdio against a fake MCP server. They cover allow, deny, hidden tools, redaction, queue approval with a grant, timeout, approval through elicitation, and a batch bypass attempt.

This is a from-scratch, public implementation of the human-approved AI agent gateway concept I first designed while building SecretZero.
