Case study · Post-quantum cryptography

You can't migrate cryptography you can't find

cbom-scan builds a cryptography inventory from code, configs, certificates and live TLS endpoints in seconds, then turns it into a CycloneDX CBOM, CI findings and a post-quantum readiness score.

The problem

NIST plans to deprecate RSA and elliptic-curve cryptography from 2030 and disallow it by 2035. Data encrypted today with RSA or ECDH can be recorded now and decrypted once a large quantum computer exists ("harvest now, decrypt later"). Every PQC migration strategy, including the discovery-to-migration approach I designed at Thales, starts with discovery. That is hard because cryptography is spread across source code, libraries, server configs, certificates and network endpoints.

How it works

Rules understand how each ecosystem names algorithms: Java Cipher.getInstance("AES/ECB/PKCS5Padding"), Node generateKeyPairSync("rsa", { modulusLength: 3072 }) (with the size on a later line), OpenSSL EVP_des_ede3_cbc(), JWT RS256, TLS cipher suites in both OpenSSL and IANA naming, SSH KexAlgorithms, and the new post-quantum names such as ML-KEM-768, X25519MLKEM768 and mlkem768x25519-sha256. Certificates and keys are parsed for type, size, signature algorithm and expiry.

Design decisions

  • Standards first. The output is a CycloneDX 1.6 CBOM with primitives, parameter sets, curves, modes, NIST quantum security levels and OIDs. Certificates link to their key and signature algorithms, and every occurrence carries file and line. It validates against the official schema, so it works with existing CBOM tooling.
  • Live endpoints, not just code. Python's TLS library cannot choose key-exchange groups, so the probe uses OpenSSL 3.5 to check whether a server agrees to the ML-KEM hybrid and whether it still accepts TLS 1.0 or 1.1.
  • An explainable score. Readiness is a simple, documented formula (points off per broken or quantum-vulnerable family, a bonus if PQC is already in use), so teams can track it in CI instead of arguing about a black box.
  • Tuned on real code. Running it against Python's standard library showed that the TLS rules flagged code that only defines constants like CERT_NONE. They now fire only when code actually sets insecure values, and an inline cbom-scan: ignore marker handles deliberate cases.
  • No secrets in the repo. Test certificates and private keys are generated during the test run instead of being committed.

Example finding

On its first live test, the probe confirmed that a major CDN negotiates X25519MLKEM768 for post-quantum key exchange, but still accepts TLS 1.0. Both are useful facts for a migration plan, and neither is visible in source code.

Limits

It is static, pattern-based analysis. It finds what code and configs say, not algorithms chosen at runtime or inside compiled dependencies. Pair it with a dependency SBOM and network observation for full coverage. The README credits IBM's sonar-cryptography and PQCA's CBOMkit, which do deeper, AST-based analysis for Java and Python. cbom-scan aims to be the quick, broad first pass.
